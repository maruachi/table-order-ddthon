# 사용자 스토리 (User Stories)

테이블오더 서비스의 사용자 스토리. 구성: **Hybrid(페르소나 → 기능/도메인)**, 세분화: **중간**, 인수 조건: **Gherkin(Given/When/Then)**, 우선순위: **MoSCoW**, NFR: **관련 스토리 인수 조건에 인라인**.

- 출처 요구사항: `aidlc-docs/inception/requirements/requirements.md`
- 페르소나: `personas.md` (P1 고객, P2 관리자)
- 우선순위 범례: **Must**(MVP 필수) / **Should**(중요) / **Could**(선택) / **Won't**(범위 외)

---

# EPIC C. 고객 (Customer) — P1

## C-A. 세션 / 자동 로그인

### US-C1 — 테이블 태블릿 자동 로그인 · 세션 유지 `[Must]` (FR-C1)
> **As a** 고객(테이블 태블릿),
> **I want** 최초 1회 설정 후 태블릿이 자동으로 로그인되기를,
> **so that** 별도 로그인 절차 없이 바로 메뉴를 보고 주문할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 최초 1회 로그인 설정
  Given 관리자가 매장 식별자, 테이블 번호, 테이블 비밀번호를 태블릿에 입력했고
  When 로그인이 성공하면
  Then 로그인 정보가 브라우저 로컬에 저장되고
  And 이후 앱 실행 시 저장된 정보로 자동 로그인된다

Scenario: 자동 로그인으로 메뉴 화면 진입
  Given 태블릿에 유효한 로그인 정보가 저장되어 있고
  When 고객이 앱(태블릿)을 열면
  Then 별도 입력 없이 로그인되어 메뉴 화면이 기본 화면으로 표시된다

Scenario: 잘못된 초기 자격증명
  Given 관리자가 잘못된 테이블 비밀번호를 입력했을 때
  When 로그인을 시도하면
  Then 오류 메시지를 표시하고 로그인 정보를 저장하지 않는다
```
**NFR/제약(inline)**: 로그인 정보·세션은 브라우저 로컬 저장으로 새로고침에도 유지(NFR-5). 모든 요청은 매장 식별자·테이블로 데이터가 격리되어야 한다(NFR-3).
**INVEST 메모**: 독립적으로 개발/검증 가능(다른 스토리 완료 불필요). 인증 유닛의 기반 스토리.

## C-B. 메뉴 탐색

### US-C2 — 메뉴 조회 및 카테고리 탐색 `[Must]` (FR-C2)
> **As a** 고객,
> **I want** 카테고리별로 정리된 메뉴를 보고 상세 정보를 확인하기를,
> **so that** 원하는 메뉴를 쉽게 찾아 선택할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 메뉴 기본 화면 표시
  Given 고객이 자동 로그인되어 있을 때
  When 앱이 열리면
  Then 메뉴 화면이 기본 화면으로 표시되고 카테고리별로 분류되어 보인다

Scenario: 카테고리 간 이동
  Given 메뉴 화면이 표시되어 있고
  When 고객이 특정 카테고리를 선택하면
  Then 해당 카테고리의 메뉴 목록으로 빠르게 이동한다

Scenario: 메뉴 상세 확인
  Given 메뉴 목록이 표시되어 있고
  When 고객이 한 메뉴를 선택하면
  Then 메뉴명, 가격, 설명, 이미지(URL)가 표시된다
```
**NFR/제약(inline)**: 카드형 레이아웃, 터치 친화 버튼 최소 44x44px, 명확한 시각적 계층(NFR-6). 이미지는 URL 참조만(업로드/최적화 없음). 노출은 관리자가 설정한 순서를 따른다.

## C-C. 장바구니

### US-C3 — 장바구니 관리 `[Must]` (FR-C3)
> **As a** 고객,
> **I want** 메뉴를 장바구니에 담고 수량을 조절하며 총액을 확인하기를,
> **so that** 주문 전에 원하는 구성을 자유롭게 조정할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 메뉴 추가 및 수량 조절
  Given 고객이 메뉴를 보고 있을 때
  When 메뉴를 장바구니에 추가하고 수량을 증감하면
  Then 장바구니 항목과 수량이 갱신되고 총 금액이 실시간으로 재계산된다

Scenario: 항목 삭제 및 비우기
  Given 장바구니에 항목이 있을 때
  When 특정 항목을 삭제하거나 장바구니 비우기를 실행하면
  Then 해당 항목/전체가 제거되고 총 금액이 갱신된다

Scenario: 새로고침 후에도 유지
  Given 장바구니에 항목이 담겨 있을 때
  When 고객이 화면을 새로고침하면
  Then 장바구니 내용이 그대로 유지된다
```
**NFR/제약(inline)**: 장바구니는 **클라이언트 측 임시 저장**(브라우저 로컬), 서버 전송은 주문 확정 시에만(NFR-5, FR-C3).

## C-D. 주문

### US-C4 — 주문 생성 및 확정 `[Must]` (FR-C4)
> **As a** 고객,
> **I want** 장바구니 내용을 최종 확인하고 주문을 확정하기를,
> **so that** 매장에 주문을 전달하고 주문 번호를 받을 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 주문 확정 성공
  Given 장바구니에 1개 이상의 항목이 있을 때
  When 고객이 주문 내역을 최종 확인하고 주문을 확정하면
  Then 주문이 생성되어 주문 번호가 표시되고
  And 장바구니가 자동으로 비워지며
  And 5초간 확인 화면을 표시한 뒤 메뉴 화면으로 자동 리다이렉트된다

Scenario: 주문 실패
  Given 고객이 주문을 확정했으나 서버 처리가 실패했을 때
  When 실패 응답을 받으면
  Then 에러 메시지를 표시하고 장바구니 내용을 그대로 유지한다

Scenario: 빈 장바구니 주문 방지
  Given 장바구니가 비어 있을 때
  When 고객이 주문을 시도하면
  Then 주문 확정이 비활성화되거나 안내 메시지가 표시된다
```
**NFR/제약(inline)**: 주문 정보에는 매장 식별, 테이블 식별, 메뉴 목록(메뉴명/수량/단가), 총 금액, 세션 ID가 포함된다. 첫 주문 시 테이블 세션이 시작된다(도메인: 테이블 세션).

### US-C5 — 현재 세션 주문 내역 조회 `[Must]` (FR-C5)
> **As a** 고객,
> **I want** 지금 이 자리(세션)에서 낸 주문 내역과 상태를 보기를,
> **so that** 내가 주문한 것과 진행 상황을 확인할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 현재 세션 주문만 표시
  Given 고객이 현재 테이블 세션에서 주문을 냈을 때
  When 주문 내역 화면을 열면
  Then 현재 세션의 주문만 주문 시간 순으로 표시되고
  And 이전 세션·이용완료된 주문은 표시되지 않는다

Scenario: 주문 상세 표시
  Given 주문 내역이 표시되어 있을 때
  When 특정 주문을 보면
  Then 주문번호, 주문 시각, 메뉴·수량, 금액, 상태(대기중/준비중/완료)가 표시된다

Scenario: 목록 탐색
  Given 주문이 다수일 때
  When 목록을 스크롤하면
  Then 페이지네이션 또는 무한 스크롤로 추가 주문을 확인할 수 있다
```
**NFR/제약(inline)**: 세션 격리(NFR-3) — 반드시 현재 세션 주문만. 이용 완료 처리(US-A6) 후에는 목록이 비워진다.

### US-C6 — 주문 상태 실시간 업데이트(고객 화면) `[Could]` (FR-C5 선택사항)
> **As a** 고객,
> **I want** 주문 상태가 바뀌면 새로고침 없이 화면에 반영되기를,
> **so that** 준비 상황을 즉시 알 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 상태 실시간 반영
  Given 고객의 주문 내역 화면이 열려 있고
  When 관리자가 주문 상태를 변경하면
  Then 고객 화면의 해당 주문 상태가 새로고침 없이 갱신된다
```
**NFR/제약(inline)**: 선택 기능 — MVP 필수 아님. 미구현 시 US-C5는 화면 진입/새로고침 시점 기준으로 상태를 표시한다.

# EPIC A. 관리자 (Admin) — P2

## A-A. 인증

### US-A1 — 매장 관리자 로그인 · JWT 세션 `[Must]` (FR-A1)
> **As a** 매장 관리자,
> **I want** 매장 계정으로 안전하게 로그인해 세션을 유지하기를,
> **so that** 근무 중 관리자 기능을 지속적으로 사용할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 로그인 성공 및 세션 유지
  Given 유효한 매장 식별자, 사용자명, 비밀번호가 있을 때
  When 관리자가 로그인하면
  Then JWT가 발급되고 16시간 동안 세션이 유지되며
  And 새로고침 후에도 세션이 유지된다

Scenario: 16시간 후 자동 로그아웃
  Given 로그인 후 16시간이 경과했을 때
  When 관리자가 요청을 보내면
  Then 세션이 만료되어 자동 로그아웃되고 재로그인이 요구된다

Scenario: 로그인 실패 및 시도 제한
  Given 잘못된 자격증명으로 반복 로그인을 시도할 때
  When 허용된 시도 횟수를 초과하면
  Then 로그인 시도가 제한되고 오류 메시지가 표시된다
```
**NFR/제약(inline)**: 비밀번호는 bcrypt 해싱, 로그인 시도 제한 적용(NFR-2). 모든 관리자 요청은 매장 식별자로 데이터가 격리된다(NFR-3).

## A-B. 실시간 주문 모니터링

### US-A2 — 실시간 주문 대시보드(SSE) `[Must]` (FR-A2)
> **As a** 매장 관리자,
> **I want** 테이블별 주문을 실시간 그리드로 모니터링하기를,
> **so that** 신규 주문을 놓치지 않고 즉시 대응할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 신규 주문 실시간 표시
  Given 관리자가 대시보드를 열고 있을 때
  When 고객이 새 주문을 생성하면
  Then 해당 주문이 2초 이내에 대시보드에 나타나고 시각적으로 강조된다

Scenario: 테이블별 그리드 표시
  Given 대시보드가 열려 있을 때
  When 화면을 보면
  Then 테이블별 카드가 그리드로 표시되고
  And 각 카드에 테이블의 총 주문액과 최신 주문 n개 미리보기가 표시된다

Scenario: 테이블별 필터링
  Given 여러 테이블의 주문이 표시되어 있을 때
  When 관리자가 특정 테이블로 필터링하면
  Then 해당 테이블의 주문만 표시된다
```
**NFR/제약(inline)**: 실시간 업데이트는 **Server-Sent Events(SSE)**로 구현, 신규 주문 2초 이내 표시(NFR-1). 자기 매장 주문만 표시(NFR-3).

### US-A3 — 주문 상세 조회 및 상태 변경 `[Must]` (FR-A2)
> **As a** 매장 관리자,
> **I want** 주문 카드를 열어 전체 메뉴를 보고 조리 상태를 변경하기를,
> **so that** 진행 상황을 관리하고 고객에게 정확한 상태를 제공할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 주문 상세 열람
  Given 대시보드에 주문 카드가 있을 때
  When 관리자가 주문 카드를 클릭하면
  Then 해당 주문의 전체 메뉴 목록(메뉴명/수량/단가)과 총액이 표시된다

Scenario: 주문 상태 변경
  Given 주문 상세가 열려 있을 때
  When 관리자가 상태를 대기중/준비중/완료 중 하나로 변경하면
  Then 주문 상태가 갱신되고 대시보드에 반영된다
```
**NFR/제약(inline)**: 상태 변경은 SSE를 통해 다른 관리자 화면(및 US-C6 활성 시 고객 화면)에 전파된다(NFR-1).

## A-C. 테이블 관리

### US-A4 — 테이블 태블릿 초기 설정 `[Must]` (FR-A3)
> **As a** 매장 관리자,
> **I want** 테이블 태블릿의 번호와 비밀번호를 초기 설정하기를,
> **so that** 태블릿이 자동 로그인 상태로 운영될 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 태블릿 초기 설정
  Given 관리자가 새 테이블 태블릿을 설정할 때
  When 테이블 번호와 비밀번호를 입력해 설정하면
  Then 자동 로그인이 활성화되고 태블릿이 메뉴 화면으로 운영될 수 있다
```
**NFR/제약(inline)**: 설정은 US-C1의 자동 로그인 전제 조건을 만든다. 매장 식별자로 격리(NFR-3).

### US-A5 — 주문 삭제(직권 수정) `[Must]` (FR-A3)
> **As a** 매장 관리자,
> **I want** 잘못 들어온 주문을 확인 후 삭제하기를,
> **so that** 정확한 주문/금액을 유지할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 주문 삭제 확인 후 실행
  Given 관리자가 특정 주문을 삭제하려 할 때
  When 삭제를 요청하면 확인 팝업이 표시되고
  And 확인하면 해당 주문이 즉시 삭제되며
  Then 테이블 총 주문액이 재계산되고 성공 피드백이 표시된다

Scenario: 삭제 실패 처리
  Given 삭제 요청이 실패했을 때
  When 실패 응답을 받으면
  Then 실패 피드백을 표시하고 주문은 유지된다
```
**NFR/제약(inline)**: 삭제는 대시보드/총액에 실시간 반영(NFR-1).

### US-A6 — 테이블 세션 종료(이용 완료) `[Must]` (FR-A3, 도메인 핵심)
> **As a** 매장 관리자,
> **I want** 손님 이용 완료 시 테이블 세션을 종료하기를,
> **so that** 다음 손님이 이전 내역 없이 새로 시작할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 세션 종료 및 이력 이관
  Given 테이블에 진행 중인 세션과 주문이 있을 때
  When 관리자가 이용 완료(세션 종료)를 실행하면
  Then 해당 세션의 주문이 세션 ID와 완료 시각과 함께 과거 이력으로 이동하고
  And 현재 주문 목록과 테이블 총 주문액이 0으로 리셋된다

Scenario: 새 세션 시작
  Given 세션이 종료된 테이블에서
  When 새 고객이 첫 주문을 내면
  Then 새로운 테이블 세션이 시작되고 이전 내역은 현재 화면에 표시되지 않는다
```
**NFR/제약(inline)**: 세션 라이프사이클은 서비스의 핵심 도메인 로직(도메인: 테이블 세션, 주문 이력). 리셋은 고객 화면 US-C5에도 즉시 반영.

### US-A7 — 과거 주문 내역 조회 `[Should]` (FR-A3)
> **As a** 매장 관리자,
> **I want** 테이블별 과거(이용 완료) 주문 내역을 조회하기를,
> **so that** 지난 이용 기록을 확인·정산할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 테이블별 과거 이력 조회
  Given 이용 완료된 세션 이력이 있을 때
  When 관리자가 특정 테이블의 과거 내역을 조회하면
  Then 시간 역순으로 주문번호, 시각, 메뉴, 총액, 이용완료 시각이 표시된다

Scenario: 날짜 필터
  Given 과거 이력 목록이 표시되어 있을 때
  When 관리자가 날짜 필터를 적용하면
  Then 해당 기간의 이력만 표시된다
```
**NFR/제약(inline)**: 자기 매장 이력만 조회(NFR-3). SQLite 영속 저장(NFR-4).

## A-D. 메뉴 관리

### US-A8 — 메뉴 관리(CRUD 및 노출 순서) `[Must]` (FR-A4)
> **As a** 매장 관리자,
> **I want** 메뉴를 카테고리별로 등록/수정/삭제하고 노출 순서를 조정하기를,
> **so that** 고객에게 최신의 정확한 메뉴를 제공할 수 있다.

**Acceptance Criteria**
```gherkin
Scenario: 메뉴 등록
  Given 관리자가 메뉴 관리 화면에 있을 때
  When 메뉴명, 가격, 설명, 카테고리, 이미지 URL을 입력해 등록하면
  Then 필수 필드와 가격 범위가 검증된 뒤 메뉴가 저장된다

Scenario: 메뉴 수정 및 삭제
  Given 등록된 메뉴가 있을 때
  When 관리자가 메뉴를 수정하거나 삭제하면
  Then 변경이 저장되고 고객 메뉴 화면에 반영된다

Scenario: 노출 순서 조정
  Given 카테고리에 여러 메뉴가 있을 때
  When 관리자가 노출 순서를 조정하면
  Then 고객 메뉴 화면(US-C2)에 해당 순서로 표시된다

Scenario: 데이터 검증 실패
  Given 필수 필드 누락 또는 가격이 허용 범위를 벗어났을 때
  When 저장을 시도하면
  Then 검증 오류가 표시되고 저장되지 않는다
```
**NFR/제약(inline)**: 이미지는 URL 참조만(업로드/최적화 없음). 매장별 격리(NFR-3), SQLite 영속(NFR-4).
